# Конституция проекта NASA Asteroid Tracker

## Обязательные технические правила

1. Серверная часть проекта реализуется на Rust: HTTP-сервер — `axum`, сетевой HTTP-клиент — `reqwest`, сериализация и десериализация — `serde` и `serde_json`. Веб-интерфейс реализуется как HTML, CSS и JavaScript.
2. NASA API вызывается только на Rust-сервере через слой сетевого клиента. Браузерный UI обращается только к локальному API приложения; он не должен напрямую обращаться к NASA.
3. Разбор ответов API отделён от UI и устойчив к отсутствующим или неизвестным полям ответа. Внутренние типы приложения не должны зависеть от полного JSON-ответа NASA.
4. Локальный кэш хранится в JSON-файле в стандартной папке данных приложения, полученной через системный механизм определения пользовательских директорий. Не записывать кэш в текущую рабочую директорию.
5. Дата проверяется как реальная календарная дата формата `ГГГГ-ММ-ДД` до отправки запроса. Невозможные даты, в том числе `31 февраля`, не должны попадать в сетевой слой.
6. Ошибки сети, API, декодирования JSON и файлового кэша должны сохранять различимый контекст и быть понятны пользователю. Не подменять ошибку пустым успешным результатом.
7. Секреты и ключи NASA API не хранятся в исходном коде, репозитории или браузере. Rust-сервер читает ключ из `NASA_API_KEY`; если ключ не задан, используется публичный `DEMO_KEY` с отображаемым предупреждением о лимитах.

## Инженерные требования

- Разделять UI, модели и сервисы на небольшие модули с явными границами ответственности.
- Покрывать тестами валидацию дат, преобразование ответа API, работу с кэшем и сценарии UI, которые возможно проверить без сети.
- Сетевые тесты не должны требовать реального NASA API или секретного ключа; использовать подменяемый HTTP-клиент или локальный тестовый сервер.
- Сохранять работу веб-приложения при отсутствии интернета: при наличии данных для выбранной даты показывать кэш и явно помечать его как сохранённый ранее.
- Сервер по умолчанию привязывается только к `127.0.0.1`, чтобы не публиковать локальный сервис и прокси NASA API в локальной сети.
- Использовать осмысленные небольшие коммиты и отдельные ветки для спецификаций, реализации и тестов. Изменения интегрировать в `main` через Pull Request, не прямым push.

Изменения этой конституции должны сопровождаться обновлением зависимых спецификаций и задач.
